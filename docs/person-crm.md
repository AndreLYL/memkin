# Person CRM

Memkin's person memory lives in its existing PostgreSQL/PGlite database. A person
has a stable page ID, structured profile, source records, interactions, facts,
and relationships. Names alone never identify a person.

## Implementation contract

- Manual recording and organization work without an LLM. Text, dictated text,
  and imported transcripts share the same capture API; audio transcription is an
  upstream responsibility.
- Source text is saved before extraction and remains immutable. `captured_at`
  records when the source was originally captured, `ingested_at` when Memkin
  received it, and event time separately records when something happened.
- Zoned timestamps retain the supplied representation and IANA timezone. Partial
  dates and unknown event times stay partial or unknown. Future plans do not
  silently become current addresses, jobs, or completed interactions.
- AI output is an editable proposal, with source quotes and explicit identity
  choices. Applying a proposal is transactional and idempotent. Corrections keep
  revision history and reject stale writes.
- Person pages are derived searchable views over structured data; CRM data cannot
  be accidentally replaced through the generic page editor or legacy merge.
- The UI provides people, profiles, capture, source review, and separate source
  and event timelines. REST and MCP expose the same validated operations.

## Use it

Open **人物档案** (`/people`) to create or edit a person, then choose **记一次交流**.
Alternatively open **随手记** (`/records`), paste a note or transcript and save it
first. Specify the original capture time for an imported recording, rather than
the import time. The source screen supports manual organization without a model:
add the people involved, then interactions, facts or relationships. Mark a person
as a participant or merely mentioned, set topics and date precision, and confirm.

The profile includes names/aliases, gender, multiple contacts, addresses with
validity, and birthdays with a known year/month/day or just month/day. Gregorian
and lunar birthdays are distinct; leap lunar months are explicit. An existing
legacy person page can be adopted through `page_slug` in REST/MCP. Adoption is
explicit; a shared name never joins two profiles.

Use the profile timeline's **事情发生时间** and **原始记录时间** selectors to switch
between event and source chronology. Exact topic and role filters can be combined
with time ranges. Plans and uncertain facts stay labelled. Unknown event dates
appear after dated entries and are excluded from bounded event-time queries.

### AI suggestions

Configure an OpenAI-compatible or Anthropic model in Memkin's existing settings.
The CRM provider resolves settings lazily, including after reload, and never uses
the generic CLI's mock fallback as an actual extraction. Without a provider,
extraction reports `UNAVAILABLE`; the original text remains available for manual
organization. Audio files themselves require upstream transcription; `voice`
captures transcribed text, including text from a recording device.

AI sees only the selected source and its original time context. Its response is
validated and saved as a pending proposal with literal source quotes. Names are
temporary references. The UI requires choosing an existing person or creating a
distinct profile for every reference. Proposed profile fields require a separate
confirmation because arrays such as phone numbers replace the corresponding
field. Applying uses current profile revisions; stale proposals return a conflict.

### Corrections and evidence

An entry correction keeps the previous value, reason, revision and save time.
Source text, source timestamps and ingestion timestamps never change. Correcting
participants also rebuilds derived person associations, graph links and searchable
person-page blocks. Explicit capture associations remain, so a source intentionally
attached to a person is not lost after correcting an extracted mention.

Handwritten content outside the generated person-page block is preserved. Generic
page writes cannot erase that block or change the CRM person's name/type. Legacy
merging rejects CRM profiles before mutating behavior counters. Explicit slug
renaming preserves the page ID and therefore the CRM identity.

## Time contract

| Field | Meaning |
| --- | --- |
| `captured_at_input` | Exact source timestamp text supplied at capture, including its offset |
| `captured_at` | The same instant, normalized for sorting and filtering |
| `timezone` | IANA timezone for source context, e.g. `Asia/Shanghai` |
| `ingested_at` | Database ingestion time, generated by Memkin |
| `time` | Interaction event time, independently known, partial or unknown |
| `valid_from` / `valid_until` | Fact or relationship validity, independently known, partial or unknown |
| `recorded_at` | Time a profile/entry revision was saved |

For example a note captured at `2026-10-03T19:07:00+08:00` may describe an interaction
on `2026-10-02`. Importing it in November preserves both dates and records a new
November ingestion time. Relative dates are interpreted against October 3. A
planned move in November remains a plan and does not update the current address.

Time values have `{value, precision, timezone?, original?}`. Supported precision is
`unknown`, `year`, `month`, `day`, `minute` and `second`; unknown uses `value: null`.
Year/month/day values are calendar dates; minute/second values are ISO datetimes
with an offset. Partial calendar dates use timezone-aware interval bounds only for
overlap queries, retaining the original precision in all results. Interactions use
event time; fact/relationship timeline positions use validity-start time. Date-only
API filters are UTC, inclusive of the end day; explicit datetime upper bounds are
exclusive. The Web UI converts local-midnight boundaries to the corresponding
absolute instants before filtering.

## REST and MCP

All REST paths are under `/api/crm` and inherit Memkin's existing bearer auth.

| Operation | REST | MCP |
| --- | --- | --- |
| Find/read people | `GET /people`, `GET /people/:id` | `crm_list_people`, `crm_get_person` |
| Create/update profile | `POST /people`, `PUT /people/:id` | `crm_create_person`, `crm_update_person` |
| Capture/read sources | `POST /records`, `GET /records`, `GET /records/:id` | `crm_capture_record`, `crm_list_records`, `crm_get_record` |
| Manual/AI proposal | `POST /records/:id/proposals`, `POST /records/:id/extract` | `crm_create_proposal` (with/without `data`) |
| Review proposals | `GET /records/:id/proposals` | included in `crm_get_record` |
| Confirm proposal | `POST /proposals/:id/apply` | `crm_apply_proposal` |
| Recall timeline | `GET /timeline` | `crm_timeline` |
| Correct entry | `PUT /entries/:id` | `crm_correct_entry` |
| Revision history | `GET /history/:type/:id` | `crm_history` |

MCP read-only mode exposes six CRM read tools and hides all six writes. Use stable
person IDs and `expected_revision` for changes. Source capture accepts optional
`external_id`, unique per source kind: replaying identical input returns the original
record; conflicting content, capture time or explicit associations returns 409.
Applying the same proposal twice returns the original result without duplication.

Example capture:

```json
{
  "content": "今晚和小林聊了工作，他说下个月准备搬家。",
  "source": "voice",
  "captured_at": "2026-10-03T19:07:00+08:00",
  "timezone": "Asia/Shanghai",
  "external_id": "recorder:2026-10-03:001",
  "person_ids": [42]
}
```

Manual proposals contain `people: [{key, name}]` and `entries`. Each entry is an
`interaction`, `fact` or `relationship` with `evidence: {quote}`. References use the
temporary person keys. Confirm with `identities: {key: {person_id, expected_revision}}`
or `{key: {new_person: profile}}`. Saved entries use numeric person IDs encoded as
strings. No model-supplied name, alias, cache entry or pinyin match can silently
resolve a CRM person.

## Storage and validation

Migration M013 adds CRM tables on the existing PostgreSQL or PGlite engine.
Structured rows are authoritative; generated person pages and typed `crm:` graph
links are derived retrieval views. Source and revision immutability is enforced by
database triggers as well as the API. New fields require no external graph database.

Use a full database backup to retain CRM tables. The legacy Markdown page export
contains derived person pages, not a complete backup of structured CRM state and
immutable sources. For PGlite, stop Memkin before copying the full data directory;
for PostgreSQL, include all CRM tables in the normal database backup.

Automated tests cover source preservation, identity ambiguity, temporal precision,
DST, source/event filters, plans, transactions, replay, conflicts, corrections,
legacy compatibility, REST auth and real MCP SDK calls. Browser and production CLI
validation use synthetic data. Real-model extraction quality and the private
holdout quality gate require configured model access and private evaluation data;
synthetic functional tests do not establish real-session extraction quality.
